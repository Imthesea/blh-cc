# 找 Bug 的方法论（复盘沉淀）

> 记录一次耗时长、方向反复跑偏的 bug 排查（agent_team REPL 卡死）之后的教训，用于后续遇到同类问题时按此流程执行，避免再犯。

## 一、核心原则

**先复现 + 先定位，再谈修复。禁止先猜根因再改代码。**

判断顺序永远是：

1. 先确认「现象」：到底卡在哪、表现是什么、有没有日志。
2. 再定位「位置」：用日志探针/断点确认代码停在哪一行、哪个状态。
3. 最后才「修复」：只改能解释现象的那一处。

## 二、标准排查流程

### 1. 先复现（能跑就直接跑）

- 只要环境可用（`.env` 配好、启动命令明确），第一件事就是**真实跑一遍**，而不是靠读代码想象。
- 复现要尽量贴近用户真实环境（真实终端 TTY 与 pipe 行为不同，注意区分）。
- 复现时记录关键输出和时间点，确定「最后一次正常输出」和「最后一次异常状态」。

### 2. 打日志探针定位到具体一行

- 在怀疑的路径上插入探针（`console.error("[DBG] ...")`），确认执行流走到哪。
- 用探针回答一个明确问题，例如：**「循环有没有回到 `readLine`？」**
- 不要把探针撒得满文件都是；先在最可能的分界点打 1-2 处，看结果再决定下一步。

### 3. 区分「进程真停住」还是「界面没恢复」

- 「卡死」至少有两种完全不同的根因：
  - **真死锁/阻塞**：代码停在某个 await/锁上，进程不再往下走。
  - **界面假死**：逻辑已结束、进程仍在等输入，但提示符/界面没刷新。
- 判断方法：在循环末尾/输入点打探针，看是否到达。到达了 = 不是死锁，是显示层问题。
- 这一步是本次排查的关键转折点，之前一直卡在「当死锁去查」，方向就错了。

### 4. 日志先行，交叉验证

- 日志里往往已经有强线索。本次日志最后是 `event=stop`，之后无新事件，逻辑已收敛——早就暗示不是锁问题。
- 先看日志的最后几行，再决定往哪打探针，不要跳过日志直接猜。

### 5. 改一处，验证一处

- 每次改动前先问自己：**这一改能被一条日志或一个测试验证吗？** 验证不了的改动不做。
- 改了两次方向都不对，立刻停手，回到复现证据重新定位，而不是继续换方向猜。

## 三、本次 bug 的实际结论

- 现象：agent_team 任务跑完后，终端不再显示 `>`，无法继续输入。
- 真根因：后台 `teamTurn` 收尾时用 `console.log` 输出，覆盖了前台 `readline.question("> ")` 挂起的提示符，导致提示符消失，看起来像卡死。
- 实际状态：进程逻辑已结束，仍在 `readLine` 等待输入，不是死锁。
- 修复：`print` 在等待输入时清行 → 打印 → 重新画 `>`。

## 四、下次遇到同类问题时的自查清单

- [ ] 我是不是又在「读代码猜」而不是「跑起来测」？
- [ ] 环境可用吗？可用就先复现。
- [ ] 我有没有用日志/探针定位到「具体卡在哪一行」？
- [ ] 我区分了「真死锁」和「界面假死」吗？
- [ ] 日志的最后几行我看过了吗？它指向哪里？
- [ ] 这次改动能被一条日志或测试验证吗？
- [ ] 连续两次改错方向了吗？是的话先回到证据，别再猜。

## 五、底线

**没有证据就下结论、没有验证就改代码，是效率最低的工作方式。** 排查类问题永远先拿到「停在哪一行」的实证，再动手。
